# S3 / Backblaze B2

Store backups in any S3-compatible object storage: AWS S3, Backblaze B2, MinIO, Wasabi, and others.

## Create a scoped bucket + key

1. Create a **bucket** dedicated to backups.
2. Create an **access key / secret scoped to only that bucket**:
   - **AWS** — an IAM policy granting object read/write on just that bucket.
   - **Backblaze B2** — an application key restricted to the bucket.
3. Note your provider's **S3 endpoint**.

## In DockBack

**Settings → External Backup Destinations → Add Storage Provider → S3 / Backblaze B2:**

| Field | Value |
|-------|-------|
| **Display name** | A label you choose |
| **Endpoint** | e.g. `s3.amazonaws.com` (AWS) or `s3.us-west-002.backblazeb2.com` (B2) |
| **Region** | e.g. `us-east-1` (optional, provider-dependent) |
| **Bucket** | The backup bucket |
| **Access key / Secret key** | The scoped credentials |
| **Sub-path** | Optional key prefix inside the bucket |

**Test Connection**, then **Add Destination**.

## Object Lock — immutable, ransomware-proof backups (the 1 in 3-2-1-1-0)

S3/B2 **Object Lock** makes uploaded backups **WORM** (write-once-read-many): once written they **cannot be deleted or altered — not even with these credentials** — until the lock expires. This is the single strongest protection against ransomware or a stray `prune` destroying your only backups.

To enable it:

1. **Create the bucket with Object Lock enabled.** This can only be set at bucket creation (AWS: "Object Lock = Enable"; Backblaze B2: enable Object Lock on the bucket). You can't turn it on later.
2. In DockBack's destination form, set **Object Lock → Governance or Compliance** and a **Retention (days)**:
   - **Compliance** — *no one* (not even the account root) can delete before expiry. Strongest; irreversible.
   - **Governance** — like compliance, but holders of a special permission can override. Use if you want a break-glass.
3. **Strongly recommended: use an append-only key** — one that can `PutObject`/`PutObjectRetention` but **not** `DeleteObject`. Then even a fully compromised DockBack host can't erase your backups.

4. **Verify it's real — press Test Connection.** DockBack runs a **non-destructive Object Lock preflight**: it asks the bucket whether Object Lock is actually enabled and reports one of three results right in the form:
   - ✓ *green* — "Object Lock is enabled on this bucket" (with the bucket's default retention). You're genuinely immutable.
   - ✗ *red* — "You enabled Object Lock, but the bucket does NOT enforce it." The bucket was created without Object Lock, so backups here would **not** be immutable — recreate the bucket with Object Lock on.
   - *amber* — "Couldn't verify Object Lock." Your key can't read the lock config (common with a strict append-only key). That's fine: WORM still applies on upload if the bucket was created with Object Lock.

   This closes the biggest footgun — believing you're ransomware-proof when the bucket never enforced it.

How DockBack behaves with a locked destination:

- Every uploaded object gets the retention period you chose; the **Backups** view shows an **Immutable** badge with the lock-expiry date.
- **Retention/prune keeps a backup whole while its immutable copy is still locked** (the local copy is kept restorable alongside it), and never tries to delete the locked object. After the lock expires, normal pruning resumes. Size your retention period accordingly.

## Notes

- DockBack writes only under `bucket` + `sub-path` (prefix). Scope the key to the bucket for least privilege.
- For HTTP-only endpoints (e.g. a local MinIO), the backend supports an insecure mode; prefer HTTPS wherever possible.
- Object stores don't report free space the way a filesystem does, so a capacity bar may not appear for S3 destinations.
